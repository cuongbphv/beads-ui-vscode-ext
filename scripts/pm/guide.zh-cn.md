# 跑完一整圈

[English](guide.md) · [Tiếng Việt](guide.vi.md)

九个技能，一个闭环。你写规格文档，看板被填满，活儿被做完，然后看板告诉你进展到哪、什么时候能交。
接着写下一份规格，再跑一圈。

```
        markdown 规格文档
                │
                ▼
         bead-split ──────────► 看板上生成 epic + 子任务
                │
                ▼
        bead-estimate ────────► 每个子任务都有了工作量
                │
                ▼
        bead-pm-loop ─────────► 先过门禁，再做一轮
           │      │              （bead-loop → bead-take，或 bead-fleet）
           │      └───────────► bead-report    现在到哪了
           │                    bead-forecast  什么时候能交
           ▼
        bead-audit ───────────► 「做完了」是真的做完了吗
                │
                └─────────────► 发现新活儿 → 回到 bead-split
```

图里每个技能在各个环境里的名字都一样。在 Claude Code 和 Cursor 里输入 `/bead-report`，在 Codex 里
是 `$bead-report`，除此之外没有区别。

如果只记得住一件事，就记住这个：**这个闭环有权拦住你。** 这些技能一半的工作，就是在看板处于某种状态、
继续跑只会产出一个「听起来很有把握但其实是错的」答案时，拒绝继续。它停下来，是它在干活，不是它出故障。

## 跑第一轮之前

你需要 `bd` 命令行、一个看板，以及装好的这套 kit。`doctor` 会告诉你缺哪一样，并直接把修复办法打出来，
所以先跑它，然后认真读输出：

```bash
cd ~/Projects/beads-pm-kit
bin/bd-kit doctor  --into ~/Projects/my-project
bin/bd-kit install --into ~/Projects/my-project
bin/bd-kit doctor  --into ~/Projects/my-project   # 再跑一次：应该是 0 failure
```

如果 `bd` 不在 PATH 里，或者项目没有 `.beads` 目录，`install` 什么都不会写——把技能装进一个跑不动它们
的仓库，只是留下一堆没人能照着做的说明。它会改为打印 `bd` 的安装命令和 `bd init`。如果你清楚自己在做
什么，`--force` 可以绕过这道检查。

装进去的文件里有两个值得记住名字。`.beads/PRIME.md` 覆盖 `bd prime`，这是把标签和工作量约定送进**每个**
环境的**每次**会话的唯一通道，哪怕当时没加载任何技能。`scripts/pm/board.py` 是所有数字的来源：
`bead-report` 和 `bead-forecast` 都调用它，这也是这两个技能不可能互相打脸的唯一原因。

## 1. 把活儿填进看板 —— `bead-split`

你手上有一份规格、路线图或计划，躺在某个 markdown 文件里。这个技能把它变成一个 epic 加一批子任务，
并按「智能体能不能自己收尾」给每个子任务分类。

```
/bead-split docs/plan.md                          # 预览，不写任何东西
/bead-split docs/plan.md --section "Phase 2"       # 只取一个小节
/bead-split docs/plan.md --apply                  # 真的创建
```

默认是预览，而且你真该看一眼预览。标签在这里改错一行就能修好，一旦上了看板就变成看不见的技术债。如果
那个文件是文档而不是规格，技能会停下来问你，而不是把一份 README 剁成一堆假任务。

每个子任务只带一个分类标签，这是整个闭环赖以成立的约定：

| 标签 | 含义 | 智能体可以做什么 |
|---|---|---|
| `auto-ok` | 收尾所需的一切都是本仓库里的代码和测试 | 全都做，包括 `bd close` |
| `auto-partial` | 代码这边能做，但收尾需要外部条件——真实 CI 变绿、真实环境 | 写完代码就停下并留注记；**不许**关闭 |
| `needs-human` | 收尾必须有人：凭据、花钱、第三方、一个决定 | 别碰 |

凡是量不出来的，就是 `needs-human`。绝对不要从标题去猜标签——没量过的任务不等于小任务。

## 2. 让它可度量 —— `bead-estimate`

没有工作量的任务，对后面所有数字来说都是隐形的。这一步就是让你的进度报告不至于变成一种「靠沉默撒谎」。

```
/bead-estimate --backfill                # 给所有没工作量的任务预览一遍
/bead-estimate --backfill --apply        # 真的写进去
/bead-estimate beads-abc123              # 单个任务，直接写
/bead-estimate --epic beads-xyz789       # 某个 epic 的子任务
```

工作量用点数，存成标签以便在看板上看得见，同时镜像写进 `bd` 自带的 `estimated_minutes`，这样脚本就
不用去解析字符串：

`size:XS` 0.5 点 · `size:S` 1 点 · `size:M` 3 点 · `size:L` 8 点 · `size:XL` 13 点

`size:L` 是任何人可以领的上限。`size:XL` 不是一个估算，而是一句承认：还没人搞清楚这活儿是什么。技能会
拒绝让它变成可领状态，并要求你拆开。epic 永远不直接估工作量；epic 的工作量是子任务之和。这既是原则，
也是自保：`bd` 会把父任务的标签复制到新建的子任务上，所以 epic 上挂一个工作量标签，会悄悄污染下面所有
的汇总数字。

估算本身来自历史，不来自感觉。技能故意先只读标题、标签和类型，因为描述里往往塞着别人的猜测，而一个你
已经看过的数字非常难从脑子里拿掉。之后它给已关闭的任务打相似度分，用那些任务**实际花了多久**来给新任务
定价：

```bash
python3 scripts/pm/board.py refclass                 # 所有没工作量的任务
python3 scripts/pm/board.py refclass --id beads-abc  # 只看一个
```

先看 `basis` 那一列，别先看数字。`refclass` 表示找到了三个以上真正相似的已关闭任务，这个建议站得住脚。
`pert` 表示没找到，得从任务自身的范围去估。`unusable` 表示唯一匹配上的，是那些创建几分钟后就被关掉的
任务——它们的时长量的是记账动作，不是真正的工作。

最后这一条值得多说两句，因为它就发生在第一块真实看板上：十七个没工作量的任务全部返回 `size:XS`，还带
着看起来很确定的中位数，而所谓的「相似任务」唯一相同的地方只是任务类型一样。一个由巧合堆成的参照组，
比承认没有参照组更糟，所以现在有了相似度下限和合理性下限，工具会直说「没有可用的参照组」，而不是编一个
出来。

## 3. 干活 —— `bead-pm-loop`

这就是你反复跑的那一轮。

```
/bead-pm-loop                      # 一个任务，带门禁
/bead-pm-loop --fleet 4            # 改成四个互不相干的任务并行
/bead-pm-loop --dry-run            # 只过门禁，什么都不做
/bead-pm-loop --report-every 3     # 每 3 轮出报告，而不是每 5 轮
```

它不决定下一个做哪个任务——那是 `bead-loop` 的事，而真正动手的是 `bead-take`，在一个独立的 git worktree
里干。`bead-pm-loop` 加的是一块看板要跑很多轮还能管得住所必需的东西，而且它在每一轮之前全都检查一遍：

- **在制品上限。** 每个负责人同时只有一个进行中的任务。超了就先把手上的收尾，别为了看起来忙而多领。
- **先估算再领取。** 候选任务必须带且仅带一个工作量标签，且不大于 `size:L`。没有工作量的，就在这一轮里
  顺手估出来，而不是跳过——估算花几分钟，跳过则毁掉之后每一次预测。
- **停滞。** 七天没人动过、或进行中超过三天的任务，都会连负责人一起列出来。绝不会被悄悄改派给别人。
- **范围膨胀。** 如果连续三周新建的点数都超过关闭的点数，闭环会停下来要你做决定：砍范围、挪日期，还是
  接受延期。跑得更快修不了范围膨胀，而假装能修，正是一个项目悄无声息死掉的方式。
- **看板不变量。** 不属于任何 epic 的任务、没有分类标签的任务、挂了工作量标签的 epic、带两个工作量标签
  的任务。这些会直接停轮，因为在一块已经坏掉的看板上求平均，比一个数字都没有更糟。

需要的时候你也可以单独调：`/bead-take <id>` 做某个特定任务，`/bead-loop` 跑一轮不带门禁，
`/bead-fleet --batch 4` 跑一个并行批次。当几个就绪的 `auto-ok` 任务改的是不同文件时，就用 `bead-fleet`：
它给每个任务一个独立 worktree，**逐一核实**每个智能体的说法而不是照信，然后一个一个 rebase 加快进合并。

## 4. 看现在到哪了 —— `bead-report`

```
/bead-report                        # 整块看板
/bead-report beads-xyz789           # 单个 epic
python3 scripts/pm/board.py report   # 同一份东西，直接调模块
```

六个小节，顺序永远一样，好让这周的报告能跟上周对着看：看板计数、完成度、流动状况、速度、风险、下一步。
某个小节没内容就打 `— none`，而不是消失。

值得细看的几处：

**完成度有两个数字，还有一个覆盖率。** 按数量算一个、按点数算一个，然后是你的未关闭任务里到底有多少
真的估了工作量。覆盖率低于 60% 时，报告会直说：按点数那个数字描述的是已完成的部分，对剩下的活儿几乎
什么都没说。在第一块真实看板上，它显示 *按点数 100%*，而 17 个未关闭任务里有 0 个估了工作量——数字没
错，但旁边没有那句提醒的话，它就毫无用处。

**被阻塞的活儿按「真正在挡路的那个」归组。** 「5 个被阻塞」这句话你没法拿去做任何事。「这 5 个都堵在
`beads-7pi` 后面，而它是 `auto-ok` 还没人领」就可以，而且不管优先级字段怎么写，这通常是整块看板上最值得
先动的一件事。

**速度是带置信档次的，不只是一个数。** 窗口内有 5 个以上带工作量的关闭任务，是 `measured`。只有 2 到 4 个，
是 `provisional`——区间被刻意放宽，并且明确指出该拿悲观日期去做计划。少于 2 个，就干脆没有日期，只列出
要怎样才配得上一个。这套东西之所以存在，是因为第一次跑的时候，它从三个已关闭任务里算出了每天 5.86 点——
一个毫无意义、但因为带小数点而显得很真实的数字。

## 5. 看什么时候能交 —— `bead-forecast`

```
/bead-forecast                          # 所有 epic
/bead-forecast --epic beads-xyz789      # 单个
/bead-forecast --apply                  # 把快照记到 epic 上
```

每个 epic 给三个日期——乐观、大概、悲观——并且**每次都**附上让区间这么宽的原因清单：没估工作量因而不在
剩余总量里的任务、被阻塞的链条以及这些日期默认哪个任务会先动、任何智能体速度都套不上去的 `needs-human`
工作，以及时长的算法里是否包含了任务在待办里干等的那段时间。缺了这份清单的预测，只是一个假装成计划的
数字。

加 `--apply` 时，它把快照以 metadata 加一条注记的形式写到 epic 上，而这也是这个技能唯一会写的东西。记下
来的意义在下一次：`forecast` 一开始就会**给自己上次的预测打分**——挪动了多少点、这个 epic 相对大概日期
还在轨道上，还是已经越过悲观日期、越过了几天、速度有没有跳动超过一倍。算术只能告诉你日期滑了。至于上面
那份清单里到底哪一条才是真正的原因，只有你能说出来，而整件事的价值就在那一句话上。

## 6. 复核那些说法 —— `bead-audit`

```
/bead-audit                          # 整块看板
/bead-audit beads-xyz789             # 单个 epic
/bead-audit auto-partial             # 带某个标签的全部任务
```

当「早就做完了」这句话开始听着有点乐观时，用它。它会散出一批只读的智能体去重新测量，每个返回 DONE、
NOT DONE 或 PARTIAL，并附上具体证据——文件和行号、跑过的命令、拿到的退出码。没有证据就算 NOT DONE。
只有口头说法就算 PARTIAL。

之后只有主循环能关闭或修改任务。这个分工很关键：一个既能裁判又能关闭的智能体，天然有把标准放松的动机。

产出是每个 epic 的前后进度对照表、一组可以直接派给智能体去清的独立提示词，以及一份需要人来处理的单独
清单。最后那份清单，通常就是下一次 `bead-split` 的来源，闭环就此合上。

## 技能不跑、而是停下来的时候

| 它说 | 背后的事实 | 怎么办 |
|---|---|---|
| 发现未分类任务 | 有人建任务时没给泳道 | 补一个带可测理由的标签，或者归为 `needs-human` |
| `size:XL`，需要拆分 | 这个估算等于承认活儿还没被理解 | 拆成子任务，再给子任务估 |
| 预测被扣下 | 带工作量的关闭任务少于 2 个；任何日期都是编的 | 给未关闭任务估工作量，关掉 5 个，再来问 |
| 覆盖率低 | 大部分未关闭的活儿没估工作量，点数那一列只描述过去 | `/bead-estimate --backfill` |
| SCOPE ALARM | 连续三周接进来的比做完的多 | 需要你决定：砍、挪，还是接受 |
| epic 挂了工作量标签 | 它下面的汇总数字已经错了 | 去掉这个标签，改为给子任务估 |
| 这看起来是文档 | 你把 `bead-split` 指向了一份 README | 指向规格文档，或者点明要取哪一节 |

以上没有一条是错误。每一条都是技能在拒绝给你一个它撑不起来的、听着很有把握的答案——而这正是它给出的
那些答案值得相信的唯一理由。

## 速查

| 技能 | 用来做什么 | 会写看板吗 |
|---|---|---|
| `bead-split` | markdown 规格 → epic + 已估工作量且已分类的子任务 | 只在 `--apply` 时 |
| `bead-estimate` | 用可度量的历史给任务估工作量 | 单个 id 会写；`--backfill` 和 `--epic` 只在 `--apply` 时 |
| `bead-take` | 一个任务、一个 worktree、带证据关闭 | 会 |
| `bead-loop` | 每轮一个就绪任务 | 会 |
| `bead-fleet` | 并行批次，每个任务一个 worktree | 会 |
| `bead-pm-loop` | 同样的轮次，外加门禁和报告节奏 | 会 |
| `bead-report` | 现在到哪了 | 不会 |
| `bead-forecast` | 什么时候能交 | 只在 `--apply` 时，且只写 metadata 加一条注记 |
| `bead-audit` | 「做完了」是真的吗 | 会，且只有主循环写 |

它们都不会执行 `git push` 或 `bd dolt push`。它们只报告改了哪些文件，以及自己**没有**执行的命令。这是
故意的：只要历史保持线性且没推上去，一条 `git reset --hard` 就能把整晚的无人值守跑动全部撤销——而这是
这一整套东西唯一的安全网。

## 改一个技能

`.claude/`、`.cursor/` 和 `.agents/` 下面的文件都是生成出来的。每个文件带一行 stamp，直接改其中某个文件，
意味着 `bd-kit update` 会**拒绝**覆盖它，而不是悄悄把你的修改扔掉。要改就改 kit：

```bash
cd ~/Projects/beads-pm-kit
$EDITOR skills/bead-report/skill.md         # 唯一一份手写副本
node tools/sync-codex.js bead-report        # 在对照它重读过 codex.md 之后
npm test && bin/bd-kit check
node tools/fixed-point.js ../my-project     # 确认没有改到不该改的地方
bin/bd-kit install --into ../my-project
```

`docs/authoring.md` 讲 token 词表和各环境专有字段。`docs/transforms.md` 列出三个环境的**所有**差异——
如果某个差异不在那份清单上，那三个环境在这一点上就不该有差异，你在已安装的副本里看到的就是漂移。

## 到底跑过了什么

这里说白一点，因为一份夸大自身验证程度的文档，比没有文档更糟。

写这套 kit 的过程中在一块真实的 75 任务看板上量过的：`board.py report`、`forecast` 和 `refclass` 的全部
模式，一份真实的 `pm.forecast` 快照写入并通过校准路径读回，以及 `bd-kit install`、`diff`、`doctor` 和
`uninstall`。上面讲到的三处「拒绝回答」——速度的置信档次、覆盖率提醒、参照组的两道下限——之所以存在，
是因为那块看板先给出过一个自信的错误答案，而每一处都有一个复现该情形的测试用例兜着。

那次没有重新端到端跑过的：`bead-split`、`bead-take`、`bead-loop`、`bead-fleet` 和 `bead-audit` 的完整流程。
这五个技能早于这套 kit，并且已经在这块看板上实际用过；kit 把它们原样搬了进来，只加了两行、统一了六处
措辞，而 `tools/fixed-point.js` 会把生成的每个环境副本跟搬迁前的文件逐一比对来证明这一点。所以请把它们
分步骤的行为当成**已记录在案**，而不是刚刚重新测过；想确切知道改了什么，读 `docs/migration.md`。
